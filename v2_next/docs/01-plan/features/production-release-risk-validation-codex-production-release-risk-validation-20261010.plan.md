미서명 내부 운영 승인, 소스 병합, 장비 설정 적합성, 성능 검증, 정식 품질 검증은 각각 별도로 기록한다. 기존 승인이 미검증 항목의 PASS를 대신하지 않는다. PDCA 점수나 문서 작성 완료율도 정식 출시 통과 기준을 대신하지 않는다.

최종 commit·버전/태그·SHA256·payload/provenance 대조, 설치/업그레이드/재시작/복구,

## 5. 항목별 조치·검증·완료 조건

### R1. 최초 적용 확인 응답 시간 초과 원인 규명

**판단:** 실패 경로가 `/api/spot/config`였다는 해석과 이미지 fact 전체 해시·행 수 계산이 초기화 잠금 안에서 지연을 만들었다는 해석은 분석 가설이다. 원인으로 확정하지 않는다.

**조치 단계**

1. 최초 적용 도우미의 요청 순서, 제한 시간, 로그, 시작 시각, 서비스·logger 세대를 복원해 시간선을 작성한다. 확인된 사실과 추론을 구분한다.
2. 연결·응답 대기·본문 수신·JSON 처리·서버 처리 시간을 분리한다. 초기화, 파일 읽기·해시·행 수 계산, 잠금 대기와 같은 시간축으로 비교한다.
3. 격리 환경에서 과거 데이터 규모의 동일 사본으로 초기 요청을 반복한다. 작은 fact와 실제 규모 fact를 대조하며 다른 조건을 고정한다.
4. 확인된 원인만 최소 보완한다. 제한 시간 연장, 검사 제거, 첫 실패 표본 누락은 해결로 인정하지 않는다.
5. 계측을 켠 조건과 끈 조건을 비교해 계측 자체의 오버헤드를 기록한다.

**검증 방법**

- 수정 전 재현과 수정 후 같은 입력·조건의 회귀시험을 비교한다.
- 초기화 중 요청, `/health` 동시 요청, 큰 fact, 느린 디스크 조건을 격리 환경에서 확인한다.
- 기존 적용 도우미의 제한 시간, 원본 오류 응답, 표준 출력·오류, 종료 코드를 보존한다.

**완료 조건(DoD)**

- 원인 설명이 로그·구간 측정·재현 결과와 일치하며 인과관계가 확인된다.
- 수정 전 실패·수정 후 통과를 입증하는 회귀 검증이 있다.
- 첫 요청을 포함한 계획된 조건에서 동일 시간 초과가 재발하지 않는다.
- 재현되지 않았거나 인과 증거가 부족하면 `UNCONFIRMED/HOLD`로 남긴다.

### R2. 200ms 기준과 전체 성능 계약 검증

**측정 계약**

- `/health`의 기존 200ms 상한과 운영 목표·경고 50ms를 구분한다. 이번 정식 출시 계획은 **계획된 각 client `/health` 요청의 전체 응답 시간 ≤200ms**를 통과 조건으로 채택한다. 이를 기존 코드가 이미 모든 요청에 정의한 조건이라고 소급 표현하지 않는다.
- 앱 시작 시간 30초 조건은 `/health` 요청 시간과 별도다. 서버 내부 시간과 client 전체 시간을 따로 기록한다.
- 첫 요청을 제외하지 않는다. 평균·p95가 최대값이나 실패 요청을 가리지 않게 한다.
- 기존 관측 계약은 `/api/data` 목표·경고 100ms/실패 500ms, SPOT 이미지 목표·경고 500ms, LCP 목표 2500ms/실패 4000ms, CLS 목표 0.1/실패 0.25다. 실패 상한이 정의되지 않은 지표에 임의 통과값을 만들지 않는다.

**조치 단계**

1. 도구 버전, 측정 시계, 요청 주기, client 수, 데이터 크기와 장비 조건을 고정한다.
2. 격리 환경 초기 시작 10회, 실제 서버 유지보수 시간의 정상 종료·시작 3회를 측정한다.
3. 정상 운전·큰 fact·이미지 저장 동시 진행 조건을 확인하고, 화면 1개와 동일 브라우저 탭 3개 조건을 비교한다.
4. `/health`, 데이터·이미지 API, 화면 성능, CPU·메모리·디스크·큐 지표를 수집한다.
5. 최종 미서명 개선 후보에 15분 초기 확인과 120분 canary를 수행한다. 이는 새 정식 후보의 검증이며, 현재 동일 미서명 운영본에 시험을 자동 추가하는 지시가 아니다.

**검증 방법**

- `/health` 요청은 2초 주기로 겹치지 않게 실행하며 첫 응답, 최대, p50·p95·p99, timeout·오류 건수를 보존한다.
- 자원 측정은 기존 계약의 warmup 120초, 주기 5초, 창 300초·선호 표본 60개를 적용한다. 최소 표본·관측 창 조건도 실제 validator와 대조한다.
- 동일 조건의 변경 전후 원시 측정값을 비교한다. 계측 영향과 50ms 경고는 별도로 기록한다.
- 전체 성능 계약의 필수 항목을 확인하고, 측정 불가 항목을 PASS로 채우지 않는다.

**완료 조건(DoD)**

- 계획된 초기·정상 운전 조건의 각 `/health` 전체 응답 시간 ≤200ms, 정상 조건 timeout 0건.
- 앱 시작 30초 조건과 필수 전체 성능 계약 통과.
- 필수 측정 누락 및 `NOT_MEASURED` 0건. 경고·상한 미정 지표는 실제 의미와 판정을 기록한다.
- 기존 `223.4887ms` 실패 기록을 보존하며 새 결과로 삭제·재분류하지 않는다.

### R3. 실제 설정과 승인 장비 조건의 일치 검증

**조치 단계**

1. 승인된 장비 식별·모델·모드·온도 범위·방사율·LowSignal·comparator·통신 조건을 기준 프로파일로 확보한다.
2. 실제 장비 화면 또는 지원되는 readback, 설정 파일의 값을 필드별로 대조한다. 알 수 없는 값을 기본값으로 추정하지 않는다.
3. `<`와 `<=`처럼 경계 판정을 바꾸는 조건은 임계값 미만·동일·초과 사례로 실제 승인 조건과 비교한다.
4. 불일치의 원인·영향을 검토한다. 필요한 변경은 승인 범위 내 유지보수 시간에 수행하며 안전 gate를 우회하지 않는다.
5. 최종 build를 기준으로 설정 attestation을 만들고, 시작 후 runtime 증거와 정상 종료 sidecar를 연결한다.

**검증 방법**

- 기존 attestation·one-command QA의 build, fingerprint, `config_drift`, comparator 및 readback 계약을 적용한다.
- readback 미지원은 기존 `not_supported` 경로와 운영자의 실제 확인 증거로 설명한다. fingerprint 일치만으로 장비 설정 일치를 주장하지 않는다.
- build 변경에 따른 fingerprint 변경과 실제 설정 drift를 구분한다.
- 기존 도구가 증명하는 필드 범위를 확인하고, 도구 밖의 승인 필수 항목도 별도 증거로 대조한다.
- attestation 생성 시 도구가 요구하는 운영자 확인과 정상 종료 상태를 지킨다.
- [Low Signal 시험 준비 검토](../../04-report/production-release-risk-validation-comparator-readiness-20261013.report.md)의
  적용 모드·정밀도 한계를 지킨다. Ratio/Multi 설명을 App1/펌웨어40.38의 검증으로
  확대하지 않으며 REST 정수 표시값의 동일성을 내부 경계값 동일성으로 간주하지 않는다.

**완료 조건(DoD)**

- 필수 승인 조건의 불일치·미확인 0건.
- 최종 build·runtime·종료 증거에서 동일한 설정 fingerprint를 확인하고 drift가 없다.
- 운영자 확인과 경계 comparator 검증 증거가 있다.
- 변경 전 백업, 변경 이유, 변경 후 검증을 보존한다. 설정 파일 보존만으로 완료하지 않는다.

### R4. 전체 CSV와 모든 이미지 전수 검증

**조치 단계**

1. 실제 설정에서 운영 경로를 확인하고, 전체 CSV·메타데이터·관찰/이미지 fact·manifest·이미지·종료 영수증을 목록화한다.
2. 파일별 경로·크기·시각·SHA256·스키마·build/logger·관측 기간과 검증 기준 시점을 기록한다.
3. 쓰기 중인 파일은 정상 종료 또는 검증 가능한 일관된 snapshot으로 확보한다. 읽는 동안 변경된 파일을 완료 처리하지 않는다.
4. 검증된 사본을 개발 PC에서 검사한다. 과거 스키마는 해당 버전 계약을 적용하며 과거 전체 자료에 현재 장비 프로파일을 소급 요구하지 않는다.
5. 기존 CSV validator에 더해 이미지 실제 바이트의 해시와 전체 디코딩, CSV/fact/파일의 양방향 연결을 전수 검사한다.
6. 시작·종료 목록을 다시 대조하고 새 파일·변경 파일의 delta를 전수 검사해 누락 없는 종료 경계를 만든다.

**검증 방법**

- CSV는 모든 행의 파싱·필수 열·스키마·sequence·허용 빈값·온도 TTL·최종 sequence·fact/manifest 개수·해시를 검증한다.
- `scripts/validate_csv_v2_shadow.py`의 `--v2`, `--metadata`, `--spot-observation-fact`, `--spot-image-fact`, `--spot-image-fact-final-manifest` 연결 검사를 활용한다. `--require-current-server-promotion-profile`은 적용 가능한 현재·신규 자료에만 사용한다.
- 기존 validator의 fact 해시·개수·경로 안전성 확인과 이미지 개별 실물 해시·디코딩 검사를 구분한다. 기존 도구만으로 모든 이미지가 검증됐다고 주장하지 않는다.
- 참조된 이미지의 존재·해시·전체 디코딩을 검사하고, 어느 기록에도 연결되지 않는 파일도 역방향으로 보고한다.
- 큰 파일은 streaming·디스크 index 방식으로 처리하되 전체 규칙과 전역 일관성 검사를 유지한다. 작은 동일 입력에서 기존 validator와 결과를 비교한다.
- 보존 기간에 따른 삭제는 당시 정책과 대상 기간 증거로 설명한다. 오래된 파일이라는 이유만으로 정상 삭제로 간주하지 않는다.

**완료 조건(DoD)**

- 고정 목록 대비 검사·분류율 100%, 총 파일·행·이미지·바이트 수 대조 완료, 원인 미분류 0건.
- 후보 생성 데이터의 손상·설명 없는 누락·해시 불일치·미완료 종료 기록 0건.
- 과거 실패·보존 기간 만료·복구 불가 자료는 원인·영향·처리 결정을 개별 기록한다. 확인 불가 항목은 HOLD로 남긴다.
- 원본 자료를 변경하지 않고, 부분 검사 결과를 전체 PASS로 표시하지 않는다.

### R5. 이전 운영본 이미지 누락 15건의 원인·영향 확인

**조치 단계**

1. 이전 운영본 `4c97d4a…`의 코드·설정·카운터·fact·로그·종료 증거를 연결한다.
2. 현재 코드의 이미지 크기 상한 초과·큐 포화 drop 경로를 확인하되, 과거 15건에 적용하려면 이전 버전에서도 같은 경로인지 확인한다.
3. drop, 저장 작업 실패, 정책상 촬영 제외, 보존 기간 삭제를 구분한다. 서로 다른 카운터를 합쳐 원인을 단정하지 않는다.
4. 가능한 경우 event 식별자로 추적한다. 식별자가 없으면 시간 구간·카운터 정산과 증거의 한계를 명시한다.
5. 격리 환경에서 이미지 크기 경계, 큐 포화, 느린 저장, 디스크 부족·권한 거부, 큐가 남은 상태의 정상 종료를 재현한다.
6. 확인된 원인에 필요한 예방·관측·복구 조치와 회귀시험을 추가한다. 카운터를 지우거나 과거 실패를 PASS로 바꾸지 않는다.

**검증 방법**

- 현재 `_enqueue_spot_image_capture`의 크기 상한 초과 및 `QueueFull` drop, 별도 worker 실패를 추적하고 이전 코드와 대조한다.
- 정책 off·수집 간격 제외처럼 drop이 아닌 경로와 구분한다.
- 기본 이미지 크기 상한 2MB, 기본 보존 기간 7일·시간별 정리처럼 현재 확인된 설정은 실제 버전·실제 운영 값과 다시 대조한다. 이 값 자체가 과거 15건의 원인 증거는 아니다.
- 원인별 수정 전후 회귀시험과 정상 종료 시 큐 drain·저장·종료 증거를 검증한다.
- 새 후보의 정상 운전에서 drop·저장 실패 0건을 확인하되 과거 사건의 종결과 별도 판정한다.

**완료 조건(DoD)**

- 과거 15건에 대한 수량 정산, 원인·영향·복구 가능성·처리 결정의 증거가 있다.
- 복구 불가라면 과거 실패 기록을 유지하고 데이터 책임자의 영향·처리 결정을 남긴다.
- 확인된 원인의 재발 방지 회귀시험이 통과하고, 새 정상 운전의 drop·저장 실패가 없으며 정상 종료가 확인된다.
- 과거 원인 증거가 부족하면 이 항목을 미완료로 유지한다. 최근 누락 0건만으로 종결하지 않는다.

5. 실제 배포 NSIS 설치본의 전체 payload를 추출해 frontend/backend manifest·출처·provenance·파일 길이/해시를 검사하고 installer/앱의 실제 미서명 상태를 기록한다.
6. 동일 설치본으로 격리 환경 신규 설치·업그레이드·재시작·이전본 복구 및 설정·데이터 호환성을 확인한다.

**검증 방법**

- installer SHA256·commit·태그·내부 build/provenance·검증 보고서를 서로 대조한다.
- 기존 릴리즈의 Node `22.22.2`, Python `3.12.6`, hash-locked 의존성, 패키지 버전과 동일 태그/SHA 검사, NSIS 산출물·payload 무결성 계약을 미서명 빌드에서도 유지한다.
- `npm run health`, frontend build, 미서명 패키지/출처·무결성 검사 및 관련 회귀시험을 최종 변경 상태에서 수행한다. 실제 명령은 package/빌드 정의를 다시 확인하고 표준 출력·오류·종료 코드를 보존한다. health에 포함된 기존 서명 도구 selftest는 도구 회귀 검사이며 실제 후보 서명 `Valid`를 요구하는 gate가 아니다.
- one-command QA의 `FINAL PASS`, validator 종료 코드 0, 같은 서비스·logger 세대의 정상 종료 증거를 연결한다.
- 누락·skip·경고·미관찰 항목을 검토한다. 필수 누락을 승인 문구나 전체 PASS 요약으로 숨기지 않는다.

**완료 조건(DoD)**

- 사용자 미서명 정책 연결, 실제 `NotSigned` 상태와 출처·payload/provenance·정확한 installer SHA256/commit/버전·태그 확인 완료.
- 최종 설치본의 필수 소스·패키지·설치·업그레이드·복구·현장 QA 모두 통과.
- 설정·성능·전수 데이터 검증 및 같은 세대의 정상 종료 증거 확보.
- 서명 요구는 사용자 지시로 제거된 항목으로 기록하고 서명 PASS로 표시하지 않는다. 미서명 운영 승인을 정식 품질 검증의 대체로 사용하지 않는다.

- 적용 전 필요한 백업·장비 조건·유지보수 시간·승인 범위·복구 호환성 확인.

### 6.2 실제 적용 후 검토의 필수 구성

- 실제 설치본 SHA256·실행 build·서비스/logger 세대·설정 fingerprint·운영자 확인.
- 정상 시작·첫 요청·정상 운전·정상 종료와 해당 시간선·영수증.
- 첫 값·최대값·분위수·timeout·오류·자원 측정과 전체 성능 계약 판정.

계획 문서의 완료 조건은 원본 브랜치명·목표·포함/제외 범위·수정 대상·단계·검증·여섯 DoD·진행 상태가 저장되고 파일명과 실제 브랜치가 일치하는 것이다. 이는 기술적 리스크 해소나 정식 출시 완료와 구분한다.
