## 1. PLAN — 목표와 확정 범위

**목표:** 최신 온도 감시를 유지하면서, 생성한 기록이 접수·저장·거절·복구 중 어디에 있는지 설명하고, 부분 쓰기 이후 중복 저장이나 거짓 정상 완료를 방지한다.

사용자가 선택한 동작을 다음과 같이 적용한다.

- 저장 장애 중에도 온도 HTTP 조회와 화면 갱신을 계속한다. 이미지·주기 진단 요청을 먼저 줄이고, 저장하지 못한 관측은 식별자와 사유를 남긴다.
- **R01 — 구현 기준:** 이 계획이 초기 `http-improvement-plan.md` 5절의 “접수 여유 대기·HTTP 수집 중단” 제안을 대체한다. 초기안은 당시 조사 기록이며 저장 장애 대응 구현에는 이 계획의 감시 유지 정책을 적용한다.
- 복구 범위는 정상 종료, 쓰기 오류, 동일 프로세스 내 재시도와 기존 스풀 복구다. 강제 종료 복구용 영속 저널은 추가하지 않는다.
- 현재 수집·표시·flush 주기를 유지한다. SPOTViewer의 주기를 복사하지 않는다.
- 기존 CSV 열과 `sample_seq`, 관측 키, single-flight, 장치 잠금, 실패 이력 및 종료 검사를 보존한다.

## 2. DO — 구현 순서와 변경 계약

모든 단계는 **행동 실패 테스트 한 개 → 최소 구현 → 관련 회귀 검사 → 필요한 정리** 순서로 진행한다. 각 테스트 전에 이름, 검증 행동, 예상 실패, 선택 이유, 빈 구현으로 통과 가능한지를 명시한다. 예상과 다른 실패가 나오면 원인부터 확인한다.

기존 모듈과 테스트 fixture를 재사용하며, 선행 대규모 리팩터링은 하지 않는다.

진행 순서는 **정책 기준 확인 → R02/R03/R04와 RR02/RR03의 접수·자원·출력 계약 및 실패 테스트 → P0 구현 → 이미지 결과 계측 → RR01–RR04를 포함한 R05/R06 압력·복구·HTTP 연동 → 신선도·운영 판정 정리**다. P1 연동은 **FR01 최초 owner 활성화 → FR02 발송 경계·계측/진단 종결 → FR03 센서별 캐시 → IC01 화면 callback** 순으로 확인한다. 자원 상한과 이미지 복구 예약 단위 정의를 P1 단계까지 미루지 않는다. 관련 확장은 기존 `CSVLoggerService`, `SpotObservationQueue`, fact/image writer와 단일 소유자 방식 안에서 수행한다.

### 1단계 — P0-1: 생산 ID와 접수 결과

- 통합 기록을 생성할 때 큐에 넣기 전에 불변 envelope를 만든다. 식별자는 `producer_instance_id + producer_seq`이며, 재시도에는 같은 envelope를 사용한다.
- **R03:** envelope에 접수 당시 `config_generation`, `required_sinks`, 출력 계약·목적지 식별자를 고정한다. 접수 판단과 설정 세대 캡처는 같은 잠금 경계에서 수행한다. 최신 캐시 갱신은 이 저장 판단과 분리한다.
- **RR02:** 저장 결과와 현재 가용성의 식별 단위는 `(sink_id, config_generation, 실제 목적지)`다. 이미지의 JPEG 목적지·연결 fact·추적 증거를 구분하고, 실제 사용할 날짜별 폴더도 목적지에 연결한다. 새 세대와 이전 세대의 미완료 출력 상태를 혼합하지 않는다.
- 온도 fact는 기존 `service_id:poll_seq`를 유지한다. 이미지도 취득 시 발급한 capture ID를 저장 재시도까지 유지한다.
- 접수 결과를 `ACCEPTED / REJECTED_FULL / REJECTED_LIMIT / REJECTED_UNAVAILABLE / REJECTED_CLOSED / DISABLED / INVALID`로 구분한다. 각각 큐 슬롯 포화, 합산 예산 초과, 현재 저장 불가, 종료, 정책 비활성, 입력 오류를 구별한다. `reason`으로 bytes·건수·스풀 상한·초기화 실패 등을 설명한다. 호출부는 결과를 명시적으로 처리한다.
- 관측 큐의 기존 Boolean API는 호환 래퍼로 유지하고, 실제 수집 경로는 상세 결과 API로 전환한다.
- 큐 거절 때문에 화면 갱신을 막거나 같은 관측을 새로운 ID로 다시 생산하지 않는다. 기본 정책은 거절된 최신 항목을 추가 재시도 큐에 쌓지 않는 것이다.

**R02 — 대기 자료의 합산 예산**

| 경로 | 최초 구현의 대기 항목 상한 | 최초 구현의 payload bytes 상한 |
|---|---|---|
| 통합 CSV | queue·deferred·buffer·inflight 합계 5,000개 논리 이벤트 | 원본 snapshot·v1/v2 출력 사본 합계 64 MiB |
| 온도 fact | queue·inflight·메모리 복구 대기 합계 256개 논리 이벤트 | 합계 16 MiB |
| 이미지 | queue·inflight·메모리 복구 대기 합계 128개 capture | 이미지 bytes·연결 snapshot 합계 128 MiB; 기존 이미지 1건 크기 제한도 유지 |
| 추적 자료 | 데이터 경로별 미확정 segment 최대 2개, 거절·정책상 제외 범위 합계 최대 4,096개 | 데이터 경로별 미확정 segment 합계 2 MiB |

- 위 값은 기존 queue 건수 상한을 재사용하고 bytes 상한을 추가한 **초기 소프트웨어 예산**이다. 검증된 최적값이나 프로세스 RSS 상한이 아니다. 실제 직렬화한 payload·출력 bytes와 추가 사본을 계수하며, 참조만 공유하는 객체는 중복 청구하지 않는다. Python 객체·기존 과거 키 인덱스 등은 별도로 계측한다.
- 접수 시 예산을 예약한다. queue에서 꺼낼 때 예약을 해제하지 않으며, 해당 payload가 저장·복구 스풀로 확인되어 이동하거나 최종 실패로 명시될 때 해제한다. 출력 사본 생성 전에 추가 예산도 확보한다. 확보할 수 없으면 새 자료를 계속 꺼내거나 버퍼를 확대하지 않는다.
- 렌더링·직렬화 중 임시 사본도 예산에 포함한다. 처리에 필요한 최소 공간을 예약하지 못한 항목은 사유 있는 실패로 종결하고 원래 접수·실패 이력을 남긴다. 오류를 `DISABLED`로 바꾸거나 몰래 버리지 않는다.
- 주 파일 장애 시 기존 fact 스풀의 총 미복구 크기는 저장 경로별 64 MiB로 제한한다. 스풀은 최대 4 MiB segment로 순차 저장하고, **fact/spool 복구 읽기**는 한 번에 최대 20건·1 MiB로 제한한다. 해당 fact/spool 단일 행도 1 MiB를 넘겨 읽지 않으며 초과 자료는 `INVALID/UNCERTAIN`과 원본 위치로 보고한다. `list(handle)` 방식의 전체 읽기는 사용하지 않는다.
- **RR03:** JPEG 복구는 한 차례 **1 capture**로 처리한다. 1 MiB fact/spool 제한을 JPEG 한 건 제한으로 재사용하지 않는다. 접수 당시 유효한 `SPOT_IMAGE_CAPTURE_MAX_BYTES`와 전체 이미지 pending 예산 안에서 bytes·연결 snapshot·필요한 임시 사본을 예약한다. 기본 한 건 제한 2,000,000 bytes는 코드 기본값이며 활성 설정은 별도 확인한다. 이미 접수한 payload의 예약은 복구로 옮길 때 승계하고 이중 예약하지 않는다. 파일을 다시 읽는 데 새 사본이 필요하면 추가 예약을 먼저 확보한다.
- JPEG는 현재 whole-capture writer 방식을 유지한다. chunk offset을 관리하는 새 복구 엔진은 추가하지 않는다. 접수 후 설정이 바뀌어도 기존 capture에는 접수 당시 한도·계약을 적용한다. 복구 단위가 1 MiB보다 크다는 이유로 기존 접수 건을 `INVALID`로 바꾸거나 전체 예산을 넘기지 않는다.
- 스풀 상한을 넘는 새로운 쓰기는 명시적으로 실패 처리한다. 기존 미복구 자료를 자동 삭제하지 않는다. 예전 단일 스풀은 읽기 전용 원본으로 보존하고 같은 제한으로 순차 복구한다.
- 새 저장 형식으로 이동할 때는 대상 segment 확정 후에만 원래 위치의 예약을 해제한다. 디스크 복구 대기 건수와 메모리 대기 건수는 별도로 표시한다.
- bytes 상한·복구 단위·segment 값은 내부 정책 상수와 계약 버전으로 관리한다. RV01/RV02에서 정상 fixture 수용, 상한 유지, 처리량을 확인하며, 조정이 필요하면 값·이유·재검사 결과를 계획에 기록한 후 적용한다.

**완료 조건:** 큐 앞·중간·끝의 거절이 ID와 사유로 설명되고, queue가 비어도 배치·inflight·추적 대기의 예산이 유지된다. 1 MiB 초과의 허용 JPEG도 같은 ID·예약으로 복구할 수 있다. 상세 ID 범위 한도 초과 시에는 정확한 전체 ID 목록을 보장하지 않고 `INCOMPLETE`와 집계 범위를 표시한다.

### 2단계 — P0-1: 생산–저장 대조와 종료 계약

- 기존 CSV 형식 2.3.1·2.4.2·2.5.2를 유지한다. 별도 버전의 추적 메타데이터에서 생산 ID를 기존 CSV 행 키와 연결한다.
- 추적 자료에는 생산 시작·종료 경계, 활성 설정 구간, 접수 결과, 저장 행 대응, 파일 식별 정보와 검증 상태를 기록한다. 저장 파일의 최소·최대 번호만으로 기대 범위를 만들지 않는다.
- 추적 메타데이터는 단일 writer가 데이터 경로·생산자 세대별 segment로 저장한다. 한 segment는 최대 1 MiB·1,000개 결과 항목이며 먼저 도달하는 상한 또는 1초의 flush 주기로 확정한다. 한 항목이 segment 상한을 넘으면 상세 내용을 무제한 보관하지 않고 추적 오류로 처리한다. 완성된 segment는 동일 디렉터리 임시 파일 후 고유 최종 이름으로 원자적 교체한다. 접수 전 영속 저장을 보장하는 저널로 취급하지 않는다.
- **RR01:** segment의 첫 미확정 결과가 들어올 때 단조 시계로 증거 확정 예정 시각을 예약하고, 뒤의 항목이 추가되어도 그 시각을 늦추지 않는다. 데이터 쓰기 대기와 정상 증거 flush 대기를 구분해 5단계 제어기에 전달한다. 예정 시각 전의 증거 pending은 장애 재처리 pending이 아니다.
- 미확정 segment 2개가 가득 차면 이 자료와 연결된 저장 경로의 신규 접수를 거절한다. 장기 보존 추적 파일에는 기존 데이터와 연결된 보존 정책을 적용하되, 미해결 결과·미복구 스풀을 공간 확보 목적으로 자동 삭제하지 않는다.
- 거절·정책상 제외 ID는 종류·사유·설정 세대가 같은 연속 범위로 압축한다. 디스크 장애 중 메모리에는 두 종류를 합해 스트림별 최대 4,096개 범위를 유지하며, 초과하면 집계는 계속하되 상세 추적 상태를 `INCOMPLETE`로 고정한다.
- **R03:** 상태와 저장 대응은 `(event_id, sink_id)`별로 관리한다. 하나의 생산 이벤트가 v1/v2에 쓰여도 생산 수는 1이다. 전체 성공은 접수 당시 `required_sinks`의 데이터와 추적 증거가 모두 확인된 경우다. 선택하지 않은 출력은 성공 수에 포함하지 않는다.
- 설정 변경 전에 접수한 항목은 이전 설정 세대·목적지·CSV 계약으로 drain한다. 변경 뒤 생산한 항목부터 새 설정을 적용한다. 이전 자료를 쓸 수 없으면 실패/미확정 상태로 남기며 소급 `DISABLED`로 바꾸지 않는다. AUTO_SAVE 해제는 신규 저장 선택을 해제하는 동작이며 기존 접수 취소가 아니다.
- 세대 번호만 저장하는 데 그치지 않는다. 고정 계약을 `_build_row/_build_v2_row`, 파일 열기, output hash, flush, closeout까지 전달한다. 이미지 writer 선택도 소비 시점의 전역 설정으로 이전 capture의 목적지를 바꾸지 않게 한다.
- 종료 순서는 생산 중지·경계 확정 → 접수 항목 drain → 파일과 ID 대조 → 종료 manifest 작성이다.

대조식은 논리 이벤트와 처리 시도를 분리한다.

```text
생산 = 정책상 제외 + 접수 + 최종 거절
각 required sink의 접수 = 증거까지 확인 + 데이터 기록·증거 대기 + 복구 대기 + 미확정 + 처리 대기 + 최종 실패
이벤트 전체 완료 = 모든 required sink의 증거까지 확인
```

각 항목은 서로 겹치지 않는 현재 상태로 집계한다. `ALREADY_COMMITTED`는 기존 완료의 재확인 결과이며 새 저장 수로 더하지 않는다. 재시도·실패 이력은 상태별 이벤트 수와 별도로 센다. 메타데이터 비활성·누락·손상, 미확정 항목 또는 예상치 못한 거절이 있으면 신규 완전성 검사를 PASS로 표시하지 않는다. CSV v1은 현재 프로세스의 파일·행 위치·고정 내용 대응 범위만 검증하며, 안정적인 키 없이 재시작 후 개별 행 ID 복구를 보장하지 않는다.

**완료 조건:** 첫·마지막 기록 손실, 종료 경쟁, 날짜·설정 세대 전환이 대조에 포함된다. v1 성공·v2 실패 또는 데이터 성공·추적 실패는 전체 성공이 아니며 기존 실패 이력이 유지된다.

### 3단계 — P0-2: 부분 쓰기와 동일 ID 재처리

- 먼저 실제 임시 파일에 20행 중 7행을 쓴 뒤 실패하는 테스트를 만든다. 쓰기 시작 전에 예외를 내는 테스트로 대체하지 않는다.
- writer 내부 결과를 `COMMITTED / ALREADY_COMMITTED / DATA_WRITTEN_EVIDENCE_PENDING / SPOOLED / UNCERTAIN / FAILED / CONFLICT`로 구분한다. 기존 외부 반환 형식이 필요한 호출부에는 호환 래퍼를 둔다.
- **R04:** 원본 envelope의 `source_payload_hash`와 최종 출력의 `output_payload_hash`를 구분한다. 원본은 재시도 횟수 등 처리 상태를 제외한 고정 payload의 canonical JSON, 출력은 계약 버전·열 순서·최종 문자열 값 목록의 canonical JSON으로 계산한다. JPEG는 원본 bytes hash와 연결 fact hash를 분리한다.
- 최종 출력 행은 최초 생성 시 한 번만 만든다. ingest 시각·행 생성 단조 시각·신선도·공정 판정·`sample_seq`를 그때 고정한다. 재시도에서 행 생성이나 공정 상태 전이를 다시 실행하지 않는다. 같은 ID·같은 고정 내용은 재처리, 같은 ID·다른 고정 내용은 충돌이다.
- 확정 순서는 **고정 행 준비 → 출력별 데이터 쓰기·부분 쓰기 대조 → `DATA_WRITTEN_EVIDENCE_PENDING` → 추적 segment 확정 → 해당 sink의 `COMMITTED` → 전체 완료 대조**다. 추적 자료 쓰기·교체가 실패하면 데이터가 이미 존재하는 행은 다시 append하지 않고 증거 확정만 재시도한다.
- 쓰기 결과가 불확실하면 해당 writer의 append를 중지하고 실제 파일을 읽는다. 완전한 행의 ID·내용을 확인한 뒤, 없는 행만 재처리한다.
- 손상된 마지막 행, 확인할 수 없는 파일 변경, 닫기 실패는 해당 저장 경로를 `UNCERTAIN`으로 남기고 수동 복구가 필요한 상태로 고정한다. 이번 범위에서는 이 상태를 우회하는 새 데이터 segment 자동 시작도 하지 않는다. 자동 절단·삭제·전체 배치 재append는 하지 않는다. 온도 감시는 계속하고 해당 경로의 신규 저장 거절을 기록한다.
- JPEG 저장 후 fact 기록만 실패한 경우 같은 capture ID와 고정 fact 내용으로 연결을 복구한다. 이미 확인된 JPEG를 fact 재시도 때문에 다시 생성하지 않는다. 기존 파일의 ID·hash·내용을 확인할 수 없으면 `UNCERTAIN`으로 남긴다. JPEG 복구의 처리 단위와 예약은 1단계 RR03을 따른다.
- 안정적인 행 키가 없는 CSV v1은 불확실한 배치를 자동 재append하지 않는다. 해당 출력의 복구 보장 한계를 명시한다.
- 데이터와 메타데이터의 파일 키·내용 hash·세대를 함께 대조한다. 메타데이터 자체 손상·누락·교체 실패도 정상 완료를 막는다. 강제 종료로 메모리에만 있던 대응 관계를 잃은 경우에는 복구를 보장하지 않는다.

**완료 조건:** 복구 후 기대 ID·고정 내용·개수가 일치하거나 미확정 상태가 유지된다. 데이터 flush 뒤 메타데이터 실패와 재시도 중 freshness 경계 통과를 시험해, 행 중복·시각/공정 판정 변경·거짓 정상 완료가 없음을 확인한다.

### 4단계 — P1-3: 이미지 저장 결과와 단조 시계

압력 제어가 정확한 결과를 참조하도록 이미지 계측을 먼저 정리한다.

- 새 upstream 취득마다 후보 ID를 발급한다. 캐시 조회에는 새 후보를 만들지 않는다.
- 결과를 `disabled`, `policy_skipped_mode`, `policy_skipped_interval`, `rejected_full`, `rejected_limit`, `rejected_unavailable`, `rejected_closed`, `rejected_oversize`, `invalid`, `pending`, `saved`, `write_failed`, `uncertain`으로 구분한다. 합산 예산 초과와 현재 저장 불가는 1단계의 상세 접수 결과와 같은 의미로 연결한다.
- 최소 저장 간격은 같은 프로세스의 단조 시계로 계산한다. 간격 기준은 마지막 **접수 성공** 시점이며, 거절된 시도는 기준을 전진시키지 않는다.
- 기존 `all` 모드의 최소 간격 적용은 유지한다. 동일 JPEG hash의 서로 다른 취득은 삭제하지 않는다.

**완료 조건:** 시계 역행·앞당김에도 저장 간격이 유지되고, 정책상 제외와 저장 실패가 별도로 집계된다.

### 5단계 — P1-1: 감시를 유지하는 저장 압력 제어

1단계의 합산 예산과 기존 요청 예산을 사용하면서 `NORMAL / PRESSURED / PERSISTENCE_BLOCKED` 상태를 추가한다. 제어기는 장치 요청·UI·`/health`와 독립된 1초 주기의 메모리 상태 평가를 사용한다. 이 주기는 센서의 수집·표시 주기 변경이 아니다.

| 상태 | 최초 구현의 전이 조건 | 동작 |
|---|---|---|
| `PRESSURED` | 활성 경로의 합산 건수/bytes/스풀 예산 중 최대 점유율 ≥80%, 또는 RR01의 최대 단계 초과 지연 ≥제어기 주기 2배 | 새 이미지 요청 예산을 평상시 예산의 절반으로 제한하고 주기 진단을 미룬다 |
| `PERSISTENCE_BLOCKED` | 예산 소진, 현재 저장 가용성 blocked/unknown, writer 중단·초기화 실패, 수동 복구가 필요한 파일 | 새 이미지·주기 진단 요청을 억제하고 온도 조회는 유지한다 |
| `NORMAL` 복귀 | 필수 출력의 현재 가용성 available, 장애 재처리 pending 없음, 최대 점유율 ≤50%, 최대 단계 초과 지연 <제어기 주기인 상태가 제어기에서 3회 연속 확인됨 | 정상 예약 pending이 계속 유입되어도 기존 요청 예산으로 복귀한다 |

- 신규 저장이 비활성이고 이전 설정 세대의 미완료 항목도 없는 경로만 평가에서 제외한다. 이전 세대의 접수 항목이 남아 있으면 해당 계약으로 drain·복구·압력 평가를 계속한다. 상태 우선순위는 BLOCKED → PRESSURED → NORMAL이며, blocked 조건이 해소됐어도 압력 조건이 남으면 PRESSURED로 이동한다. startup unknown은 writer 초기화 성공 증거 후 해제한다.
- NORMAL의 중간 구간에서는 PRESSURED 진입 조건에 도달하기 전까지 NORMAL을 유지한다. PRESSURED에서는 복귀 조건 3회 연속 확인 전까지 상태를 유지한다. BLOCKED 사유가 사라져도 NORMAL 복귀 확인이 끝나지 않았으면 PRESSURED로 완화하고, 복귀 조건이 한 번이라도 깨지면 연속 횟수를 초기화한다. 50–80% 점유와 최초 제어 주기 기준 1–2초 지연의 중간 구간으로 3회 확인을 우회하지 않는다.
- 가장 오래된 전체 나이는 queue뿐 아니라 buffer·inflight·복구·증거 대기에서 계산해 계속 표시한다. 항목이 없으면 표시값은 null이고 제어 판정에서는 대기 없음으로 처리한다. 서로 다른 clock domain의 단조 시각을 빼지 않는다.
- **RR01 — 정상 예약과 초과 지연:** 제어에는 전체 age나 poll 간격 대신 `max(0, now_monotonic - stage_due_at_monotonic)`의 최댓값을 사용한다. 통합 CSV의 데이터 단계 예정 시각은 접수 시 고정한 기존 flush 스케줄의 가장 늦은 처리 시각이며, queue·deferred·inflight 이동으로 늦추지 않는다. 즉시 처리하는 fact/image 데이터 단계는 접수 시각을 기준으로 한다. 증거 단계는 데이터 확인 후 들어간 segment의 첫 항목 기준 다음 1초 flush 예정 시각을 사용한다. 크기/건수로 조기 flush가 결정되면 그 시각을 앞당길 수 있다.
- 단계 예정 시각은 같은 단계의 재시도·새 항목 추가·제어기 평가 때문에 다시 뒤로 밀지 않는다. 실제로 데이터가 확인되어 증거 단계로 전이한 경우에만 다음 단계의 예약을 적용한다. 일반 처리 pending, 정상 예약 증거 pending, 장애 재처리 pending을 별도로 집계한다. `pending_recovery`에는 장애 때문에 확인·재처리해야 하는 항목만 포함한다.
- 최초 제어 주기 1초 기준으로 단계 초과 지연의 진입/복귀 값은 2초/1초다. 이는 기존 2배/1배 hysteresis를 **poll 간격이 아닌 제어 주기**에 적용한 내부 시작값이다. 정상 1초 증거 flush 대기는 먼저 예정 시각으로 제외한다. 현재 온도·표시·CSV flush·증거 flush 주기를 줄여 복귀 문제를 우회하지 않는다.
- 위 값은 **초기 소프트웨어 제어값**이다. 현장 허용 지연이나 최적 성능 기준으로 표시하지 않는다. RV01/RV02/RV07/RV08 및 RR-T01에서 진입 지연·정상 위상·지속 유입 중 회복·거절·bytes를 계측한다. 여유값 조정은 값·이유·재검사 결과를 기록한 후 적용한다.
- 이미 transport에 넘긴 HTTP 요청을 압력 변화만으로 취소하거나 장치 연결 수를 늘리지 않는다. task가 생성됐어도 장치 잠금을 기다리는 요청은 아직 미발송이다. 온도 요청이 예정되어 있으면 아직 발송하지 않은 이미지·주기 진단을 뒤로 미루며, FR02의 발송 경계에서 확인한다.
- 온도 관측은 최신 캐시에 계속 반영한다. 저장 불가는 저장 손실로 기록하며, 실제 HTTP 실패로 생긴 수집 공백과 구분한다.
- 상태 회복과 과거 실패 이력을 분리한다. 회복했다고 이전 거절·손실을 지우지 않는다.
- `/health`는 메모리 상태만 읽는다. 파일 스캔이나 writer 대기는 넣지 않는다.

**R05 — 현재 가용성과 독립 복구**

- `current_storage_availability(available|blocked|unknown)`, `pending_recovery`, `historical_integrity`를 별도 필드로 둔다. **RR02:** 가용성·최근 오류·성공 시각·probe 결과는 `(sink_id, config_generation, 실제 목적지)`에 연결한다. 경로 전체 available은 해당 경로의 required sink가 모두 available일 때만 성립한다. 하나라도 blocked면 blocked, blocked가 없고 unknown이 남으면 unknown이다. 누적 실패 수·기존 `writes_drained`를 가용성 값으로 재사용하지 않는다. 실제 복구 성공 시 현재 성공 시각을 갱신하되 기존 clean 종료 조건과 실패 이력은 유지한다.
- **FR01 — 최초 owner 활성화:** 서비스 시작(`start_spot_poll_loop()`의 저장 owner 연결), 저장 기능 off→on, 목적지/설정 세대 변경 때 활성 required sink를 등록하고 단일 owner의 초기화·목적지 probe를 예약한다. 첫 이미지 취득·capture 접수·UI 요청·manifest 조회를 시작 조건으로 삼지 않는다.
- thread를 생성한 것과 writer·목적지를 초기화한 것을 구분한다. `_spot_image_capture_worker()`는 큐가 비어도 해당 초기화 작업을 수행하고 결과를 메모리 상태에 게시해야 한다. 초기화 성공 및 필요한 목적지 확인이 끝나기 전에는 unknown을 available로 바꾸거나 시험용 capture를 우회 접수하지 않는다.
- FR01의 파일 I/O는 owner에서 수행한다. poll·API·`/health`는 초기화 완료나 파일 잠금을 기다리지 않는다. 살아 있는 owner를 재사용하고, 기능 off이며 과거 pending도 없으면 불필요한 owner/probe를 새로 만들지 않는다. 이전 세대 pending이 남아 있으면 기존 계약으로 drain한다. 초기화 실패·재시도·종료는 아래 단일 소유자 규칙을 동일하게 적용한다.
- writer 소유 복구 루프는 UI 요청·새 이미지 취득이 없어도 실행된다. 일시적인 I/O 실패에 대해 1→2→4→8→16→30초 상한의 단조 시계 backoff를 사용하고, 동시 복구 작업은 경로별 1개로 제한한다. 실행 중 작업에 다음 작업을 겹치지 않는다. 실패가 이어질 때만 backoff를 늘리며, 실제 데이터/증거 확정 또는 필요한 목적지 probe 성공으로 진전이 확인되면 해당 재시도 상태를 최초 1초로 되돌린다. pending이 남으면 다음 제한 단위 처리를 예약하고, 완전히 회복하면 장애 재시도 예약을 해제한다. 대기열을 조회한 것만으로 진전이라고 판단하지 않는다.
- 기존 미완료 자료를 먼저 접수 당시 계약·목적지로 확인·재처리한다. **RR03:** fact/spool 읽기는 한 차례 최대 20건·1 MiB, JPEG 복구는 1단계 예약 한도 안의 1 capture다. 증거 segment 재확정은 기존 1 MiB segment 상한을 따른다. 파일 I/O와 대조는 writer 쪽에서 수행하며 처리 단위는 OS 파일 호출의 완료 시간을 보장하지 않는다.
- **RR02 — 실제 목적지 probe:** 대기 자료가 없으면 현재 사용할 required sink의 실제 목적지마다 소유 디렉터리에 고유 임시 파일을 생성해 소량 쓰기·flush·교체·재읽기를 확인한다. JPEG 날짜별 폴더, 연결 fact 로그 폴더, 추적 증거 폴더, 복구에 필요한 스풀 경로를 해당 계약에 따라 구분한다. 로그 폴더 성공을 다른 이미지 폴더의 성공으로 재사용하지 않는다. 동일 물리 디렉터리의 probe를 공유하더라도 출력별 본 파일 오류 상태는 합치지 않는다.
- probe는 owner가 만든 임시 파일만 정리하고 기존 본 파일을 덮어쓰거나 절단하지 않는다. 성공은 해당 디렉터리의 제한된 현재 가용성 증거다. 기존 본 파일의 권한·내용·append 가능성에 관한 미해결 실패를 해소하지 않으며, 그 실패는 owner의 해당 파일 확인·복구 결과가 있어야 해제한다. 과거 데이터 복구나 전원 장애 내구성 증거로도 취급하지 않는다. 날짜·설정 세대·목적지가 바뀌면 새 목적지의 확인을 거친다.
- 초기화 실패는 기존 worker가 종료됐음을 확인한 뒤 같은 backoff로 단일 소유자를 다시 초기화한다. 기존 worker가 살아 있거나 소유권이 불명확하면 별도 worker를 중복 생성하지 않는다.
- 손상 tail·내용 충돌·소유권 불명·close 실패는 3단계의 수동 복구 상태를 유지한다. 정상 파일의 일시 실패만 자동 재확인한다. 과거의 최종 거절/실패가 남아도 현재 저장 가능 여부는 회복할 수 있지만, 과거 무결성 실패를 정상으로 바꾸지 않는다.
- 종료가 시작되면 신규 probe·재시도 예약을 중지하고 기존 종료 timeout 내에 진행 중 작업을 정리한다. 장치 잠금과 파일 잠금을 동시에 보유하지 않는다.

**R06 — 실제 HTTP 취득 억제**

- `_img_fetch_lock` 안에서 새 upstream refresh task를 생성하기 직전에 압력 상태와 양수 요청 간격을 검사한다. 이 검사는 FR02의 발송 직전 검사를 대체하지 않는다. 기존 최소 요청률 계산의 입력을 0으로 바꾸는 방식은 사용하지 않는다. single-flight waiter와 이미 dispatch한 공유 요청은 압력 변화만으로 강제 취소하지 않는다.
- PRESSURED에서는 평상시 양수 이미지 간격의 2배를 적용한다. BLOCKED에서는 새로운 upstream task를 만들지 않는다. 요청률 0의 역수를 계산하지 않는다.
- 응답 메타데이터/상태 API에 `image_upstream_suppressed`, `suppression_reason`, 억제 중 양수인 `retry_after_sec`를 추가한다. 양수 재확인 간격의 초기값은 `ceil(max(1초, 평상시 이미지 간격))`이다. 재확인은 서버 허용 상태 확인이며 센서 요청 허가가 아니다.
- 현재 센서와 일치하는 사용 가능한 캐시가 있으면 원래 취득 시각·age와 억제 사유를 유지하여 반환한다. 새 취득·신선한 이미지로 집계하지 않는다. 그 캐시가 없으면 `503`과 `Retry-After`, 사유 `storage_pressure`를 반환한다. 이 경우 클라이언트 요청 실패는 사실대로 계수하되 센서 요청 실패로 세지 않는다. 캐시 선택은 FR03을 따른다.
- 프런트엔드는 억제 사유와 마지막 이미지 나이를 표시하며 양수 간격 후 재확인한다. 사용자 조회·재시도가 와도 BLOCKED gate를 우회하지 않는다. 주기 진단만 같은 정책으로 억제하고 명시적 제어 명령의 순서·잠금은 유지한다.

**FR02 — 장치 잠금 후 발송 허용 검사**

- `_request_spot_image()`와 주기 진단의 개별 요청 경로는 `_spot_device_request_lock`을 얻은 뒤 transport 요청을 넘기기 직전에 현재 압력·양수 허용 간격·온도 우선 조건을 메모리 snapshot으로 재검사한다. 판정과 dispatch 사이에 불필요한 대기를 넣지 않는다. 장치 잠금 안에서 파일 I/O·저장 잠금 획득·backoff 대기를 하지 않는다.
- 발송하지 못하는 task는 장치 잠금을 해제하고 압력 결과로 종결하거나 양수 간격의 재확인으로 연결한다. single-flight waiter도 같은 억제 판정과 현재 센서에 맞는 캐시/503 결과를 받는다. 압력 결과가 `_record_image_error`나 일반 upstream 예외 처리로 들어가지 않도록 `_refresh_spot_image_cache()`부터 API까지 전달한다.
- 위 압력 결과·캐시/503 분기는 저장 압력 때문에 미발송된 경우에 적용한다. NORMAL에서 기본 간격이 남았거나 온도에 양보하는 경우는 IC04의 원인별 처리로 연결하며 `storage_pressure`로 바꾸지 않는다.
- 이미 transport에 넘긴 요청은 기존 timeout·종료 규칙에 따라 완료시킨다. “BLOCKED에서 신규 upstream 0건”은 BLOCKED 판정 뒤 **미발송 요청이 새로 dispatch되지 않음**을 뜻한다. 이전에 dispatch한 요청의 완료·캐시 반영과 구분한다. 그 요청이 정상 취득을 완료하면 현재 센서 일치를 확인한 뒤 실제 성공으로 기록하며, 압력 변화만으로 과거 캐시 재사용이나 미발송 억제로 재분류하지 않는다. 응답의 suppression은 해당 요청의 억제 판정이고 현재 저장 압력 상태와 구분한다.
- 진단 sweep도 각 파라미터의 dispatch 전에 검사한다. 이미 생성한 journal 항목은 `running`이나 센서 실패로 바꾸지 않고, 미발송 억제 결과로 종결해 active 항목을 남기지 않는다. 남은 파라미터를 계속 접수하지 않으며 실제 전송된 결과와 억제로 미수집된 항목을 구분한다. 이 결과를 정상 완료나 HTTP 수집 실패로 위장하지 않고 journal 소비자·집계·계약 버전을 함께 맞춘다.
- 기존 task/coalescing 계측과 이미지 `image_upstream_request_count`의 의미는 호환성을 위해 유지하고, 이미지의 기존 값이 잠금 전 refresh 진입에서 증가함을 계약에 표시한다. 새 `image_dispatch_attempt_count`·`diagnostic_dispatch_attempt_count`와 `pre_dispatch_suppressed_count`를 분리한다. dispatch 수는 허용 판정 후 transport 호출 경계에서, 미발송 억제 수는 그 경계를 넘지 않은 작업당 한 번 계수한다. waiter 수는 별도이며 한 공유 task를 여러 dispatch로 세지 않는다. dispatch 시도는 실제 장비 수신 성공을 뜻하지 않는다.
- 신규 BLOCKED 검증은 기존 이미지 task 계수만으로 판정하지 않고 dispatch 계측과 HTTP 호출 경계의 실제 시험 기록을 함께 대조한다.

**FR03 — 압력 중에도 현재 센서의 캐시만 반환**

- 압력 fallback은 `entry.image_url`과 현재 해석된 이미지 URL/센서 식별이 일치하는 캐시만 사용한다. 동일 센서의 TTL 만료 캐시는 억제 표시와 함께 반환할 수 있지만 센서 일치 조건은 완화하지 않는다. 저장 `config_generation`으로 URL 일치 검사를 대신하지 않는다.
- 센서 A의 캐시만 있는 상태에서 B로 바뀌고 취득이 억제되면 B의 사용 가능한 캐시가 없는 것으로 처리해 storage-pressure 503을 반환한다. 설정 오류는 기존 설정 오류로 처리한다. 같은 센서 캐시를 반환할 때도 기존 capture 시각·age·source를 유지하고 새 취득·저장 후보를 만들지 않는다.
- `fetch_image_async()`의 잠금 전/후 cache-hit와 refresh 완료 후 반환 모두 현재 센서 일치와 압력 메타데이터를 확인한다. in-flight 완료 중 설정이 바뀌면 기존 URL 재확인을 유지하며 이전 센서의 JPEG를 현재 센서 응답으로 내보내지 않는다.

**RR04 — API와 화면의 압력 응답 계약**

- driver의 압력 결과를 `backend/app.py::spot_image()`에서 기존 `SpotImageFetchError`의 upstream 502 변환·센서 실패 계측보다 먼저 분기한다. FR03을 통과한 현재 센서 캐시가 있으면 JPEG 200, 없으면 `503`과 JSON `detail.code="storage_pressure"`를 반환한다. downstream HTTP 503 통계는 남기고 upstream 실패 수·연속 실패 값은 증가시키지 않는다.
- 다음 헤더를 캐시 200 억제와 무캐시 503에 공통으로 전달한다. 상태 API의 동명 필드와 같은 의미·단위를 사용하며, API 생성·CORS `expose_headers`·프런트엔드 타입·parser를 함께 변경한다.

| 상태/API 필드 | 이미지 응답 헤더 | 계약 |
|---|---|---|
| `image_upstream_suppressed` | `X-Spot-Image-Upstream-Suppressed` | 명시적 `1`/`0`; 누락은 legacy unknown |
| `suppression_reason` | `X-Spot-Image-Suppression-Reason` | 억제 시 `storage_pressure`; 비억제 시 사유 없음 |
| `retry_after_sec` | `Retry-After` | 억제 시 `ceil(max(1초, 평상시 이미지 간격))`인 양수 정수 초; 비억제 시 null/헤더 생략 |

- 기존 capture 시각·age·source 헤더도 유지한다. 프런트엔드 `SpotImageResponseMetadata`와 `useSpotViewModel.selectors.ts`가 suppression과 초 단위를 읽는다. `useSpotViewModel.ts`에서는 non-2xx 일반 오류 분류 및 이미지 성공 처리보다 먼저 압력 응답을 처리한다. 캐시 JPEG는 기존 payload 검증을 거친 뒤 이전 취득 시각으로 표시하고 새 취득 성공으로 세지 않는다.
- 저장 압력에는 별도의 상태 재확인 timer를 사용한다. 유효한 양수 `Retry-After`를 따르고, 누락·잘못된 값에는 `ceil(max(1초, 현재 평상시 이미지 간격))`의 양수 fallback을 사용한다. 저장 압력임이 명시된 응답에만 이 분기를 적용한다. 같은 단일 화면 fetch의 중복 실행을 허용하지 않는다.
- 압력 재확인은 일반 통신 오류의 500/1,000/2,000ms **3회 예산을 소비하거나 초기화하지 않는다**. 압력 상태로 들어갈 때 예약된 일반 재시도/정상 갱신 timer는 정리하고 한 종류의 재확인만 남긴다. 압력이 해제되면 기존 정상 흐름으로 복귀하며, 실제 이미지 성공에 따른 일반 오류 상태 초기화는 기존 성공 경로를 따른다.
- 실제 upstream 오류·payload 오류는 기존 분류와 재시도 제한을 유지한다. 종료·화면 숨김에는 예약 timer를 해제하고, 다시 보일 때 중복 없이 상태를 재확인한다. 이미 시작한 shared upstream 요청을 이 timer 정리 때문에 취소하지 않는다. 서버 gate는 수동·자동 요청 모두에 적용한다.

**IC01 — suppression 캐시의 표시 callback 회귀 확인**

- RR04의 비초기화·timer 단일성을 `runSpotFetch()`뿐 아니라 `handleImageLoad()`까지 적용한다. 응답별 suppression과 요청/표시 식별을 연결해 현재 표시 대상에 대한 callback인지 확인한다. 압력 캐시의 onLoad는 `resetImageRecovery()`나 `scheduleNormalImageRefresh()`를 호출하지 않는다.
- 압력 재확인은 유효한 suppression 응답의 처리가 끝나고 `inFlight`를 해제한 시점에 한 번 예약한다. 캐시 200도 DOM onLoad를 기다리지 않으며 무캐시 503과 같은 양수 재확인 간격을 사용한다. 늦은 이전 이미지의 onLoad는 timer를 추가·교체하거나 retry 예산·현재 suppression 상태를 바꾸지 않는다.
- 숨김·종료·unmount가 시작됐으면 응답이 늦게 완료돼도 새 timer를 만들지 않는다. object URL 정리·표시 실패 처리·drain handshake는 보존한다. 현재 이미지의 payload/표시 오류는 압력 timer와 중복 예약하지 않고 기존 오류 분류·재시도 제한을 따르며, pressure 응답이라는 이유로 오류를 정상 표시로 바꾸지 않는다.
- 비억제 정상 응답의 현재 이미지 성공/표시 callback에서는 기존 성공 경로의 초기화·정상 갱신을 허용한다. 여기에는 압력 해제 후 정상 취득과 FR02에 따라 이미 dispatch돼 허용된 정상 완료가 포함된다. 다음 요청은 서버 gate를 다시 거친다. IC01은 새 정책 추가가 아니라 이 분기 경계를 실제 callback으로 확인하는 항목이다.

**구현 체크리스트 — IC02–IC04**

아래 체크박스는 모두 미수행 상태다. 해당 구현·회귀 결과를 확보한 뒤에만 완료 표시하며, 체크박스 수를 별도 시험 수로 합산하지 않는다.

**IC02 — 진단 중도 억제 결과와 journal 종결**

- [ ] `_refresh_spot_diagnostics()`의 파라미터별 결과를 명시 상태로 관리한다. 현재 `zip(..., strict=True)`에 짧아진 `results`를 그대로 넘기지 않고, 실제 수신 값과 미발송 억제·미수집 항목을 구분한다. 누락을 성공·parse error로 채우거나 snapshot 게시 전에 길이 예외로 끝내지 않는다.
- [ ] 이미 queued된 현재 요청만 미발송 terminal로 종결하고 active에서 제거한다. 남은 파라미터에는 가짜 요청·journal 항목을 생성하지 않는다.
- [ ] terminal/outcome의 허용 목록, 기록·복원, 집계와 실패 파일 분류를 함께 맞춘다. 기존 `mark_completed()`가 미등록 outcome을 `transport_error`로 바꾸거나 비성공 결과를 모두 실패로 세는 경로에 suppression을 그대로 넣지 않는다. 억제는 별도 계수하고 실제 timeout·HTTP·parse 실패 이력은 보존한다.
- [ ] FR-T02의 첫 파라미터 전 억제와 일부 수신 뒤 중간 억제를 확인한다. 결과/상태 게시 완료, active 누수·길이 예외·추가 dispatch·센서 실패 증가 없음과 계약에 맞는 기록 복원을 검증한다.

**IC03 — 표시 callback과 object URL·timer 수명**

- [ ] onLoad와 onError 모두 상태 변경 전에 요청/표시 식별을 검사한다. 오래된 callback은 현재 오류·retry 예산·timer·suppression을 바꾸지 않는다.
- [ ] 실제 표시가 확인된 정상 이미지와 표시 확인 전 pending을 구분한다. 새 응답이 pending을 대체할 때 불필요한 object URL을 해제하고 오류 시 복귀할 정상 이미지는 유지한다. 단일 이전 상태 슬롯을 덮으며 URL을 잃지 않게 하고, 동일 capture 재사용을 선택하면 검증 가능한 식별을 사용한다.
- [ ] 압력 timer를 `useSpotViewModelEffects`의 visibility/config 변경 정리, 종료·unmount·drain과 연결한다. 현재 표시 실패는 기존 오류 분류로 처리하며 압력 timer와 일반 오류 timer를 동시에 남기지 않는다.
- [ ] FR-T04/RR-T04에서 onLoad를 두 번 이상의 재확인 간격보다 늦추고 이전 onLoad/onError를 섞는다. 살아 있는 URL 집합이 반복마다 계속 늘지 않고 재확인 timer는 하나인지 확인한다. `useSpotViewModelEffects`를 mock하는 기존 hook 시험만으로 실제 visibility listener 연결을 통과 처리하지 말고, 같은 시험 명세 안에서 실제 effect 연결의 숨김·복귀·정리 경계를 확인한다.

**IC04 — gate 불통과 원인과 계측 분리**

- [ ] 저장 압력 때문에 미발송된 경우에만 기존 같은 센서 캐시/503·`storage_pressure`·양수 재확인 계약을 적용한다. NORMAL의 기본 간격 대기와 온도 우선 대기를 저장 압력 또는 센서 실패로 집계하지 않는다.
- [ ] NORMAL의 간격 대기는 기존 cache/간격 경로 또는 장치 잠금 밖의 양수 대기·재판정으로 연결한다. 온도 양보는 장치 잠금을 놓고 기존 공유 작업의 재판정 흐름으로 처리한다. 온도 진행을 보장하고 busy loop·추가 worker·추가 장치 연결을 만들지 않는다.
- [ ] 구현 전에 간격 기준 단조 시각과 profile 적용 위치를 명시하고 dispatch 계측과 같은 경계에서 검사한다. single-flight와 기존 timeout·종료 규칙을 유지한다. 이미 transport에 넘긴 요청의 실제 성공/오류를 사후 억제로 재분류하지 않는다.
- [ ] FR-T02/RV08에 NORMAL 대조 사례를 포함한다. 간격 대기·온도 양보 때문에 거짓 storage-pressure 503·센서 오류·잠금 안 sleep이 생기지 않는지, 재판정 시 실제 원인에 맞는 결과와 계측이 전달되는지 확인한다. 수집·표시 주기나 현장 ms 기준은 새로 정하지 않는다.

**완료 조건:** 느린 디스크·포화 상태에서도 합산 예산과 온도 감시가 유지된다. 정상 예약 증거가 지속 유입되어도 회복 후 NORMAL로 돌아온다. 실제 필수 목적지가 회복해야 available이 되며, 1 MiB 초과의 허용 JPEG도 예약 상한 안에서 복구된다. 최초 활성화와 저장소 회복은 UI·첫 이미지·큐 접수 없이 진행되고 과거 실패는 남는다. 잠금 대기 중 BLOCKED로 바뀌어도 미발송 이미지·주기 진단의 신규 dispatch는 0건이다. 이전 센서 캐시를 현재 센서 응답으로 반환하지 않는다. 화면은 압력 응답이 4회 이상 이어지고 캐시 onLoad가 발생해도 일반 retry 예산과 단일 재확인 timer를 유지하며, 해제 후 자동 재개한다.

IC02–IC04의 완료 근거는 아래 기존 시험에 연결한다. 진단 중도 억제의 결과·journal이 일치하고, 오래된 표시 callback과 URL이 현재 화면을 훼손하지 않으며, 정상 스케줄 대기를 저장 압력으로 오인하지 않아야 한다.

### 6단계 — P1-2: 새 관측과 반복 참조 구분

- 기존 poll ID, 관측 시각, clock domain, freshness 계산을 재사용한다.
- 통합 행과 화면 소비부에서 새 관측과 기존 관측 재사용을 구분한다. API 재조회만으로 관측 시각을 갱신하지 않는다.
- 서로 다른 poll에서 같은 온도가 나와도 각각 보존한다. 같은 poll을 여러 통합 행이 참조하는 것도 유지한다.
- 화면에는 값의 신선도와 저장 상태를 분리해 표시한다. 최신 값이 보여도 저장 실패 상태를 확인할 수 있어야 한다.

**완료 조건:** 같은 값의 서로 다른 poll 10건은 원시 관측 10건이고, 같은 poll을 참조하는 통합 행 10개는 원시 관측 1건·참조 10개로 설명된다.

### 7단계 — P1-4: 설정·버전·운영 판정 계약

- 기존 기능 flags를 자동 활성화하지 않는다. 실제 적용된 설정, 설정 출처, build 식별자, 검증 도구 버전·해시를 계약에 포함한다.
- 설정 fingerprint는 저장·주기·판정에 필요한 허용 목록만 사용한다. 인증정보는 포함하지 않는다.
- 기존 200/500ms 필드는 호환성을 위해 유지하고 legacy 의미를 명시한다. 신규 소비자는 `diagnostic_reference_ms`와 `operational_budget`을 분리한다.
- 운영 budget이 없으면 운영 성능은 `NOT_EVALUATED`다. 실제 HTTP 오류·저장 거절·파일 불일치는 계속 실패로 취급한다.
- 추적 메타데이터·종료 manifest·validator의 계약 버전을 함께 맞춘다. 구버전 자료는 재해석하지 않는다.
- 출력별 상태, `config_generation`, `DATA_WRITTEN_EVIDENCE_PENDING`, 단계 예정 시각·초과 지연, 목적지별 가용성·probe 결과, 복구 처리 단위와 이미지 억제 메타데이터를 새 판정 계약에 포함한다. legacy 응답에서 이 필드가 없으면 unknown/NOT_EVALUATED로 처리하며 성공 값으로 채우지 않는다. RR04의 이미지 헤더·상태 API·CORS·프런트엔드 parser 및 timer 계약을 같은 변경 단위로 검증한다.
- FR01의 owner 초기화 상태/세대, FR02의 task·dispatch·미발송 억제 구분과 진단 journal 결과, FR03의 센서 일치 조건, IC01의 응답/표시 식별과 timer 책임도 해당 계약·검증기에 연결한다. 기존 계수의 의미는 유지하며 신규 dispatch 필드가 없는 legacy 자료로 “발송 0건”을 판정하지 않는다. 원본 센서 URL이나 인증정보를 새 공개 진단 필드에 노출하지 않는다.
- IC02의 진단 terminal/outcome·복원·실패 분류, IC03의 표시 식별·실제 effect 정리, IC04의 gate 원인·dispatch 계측도 같은 변경 단위의 구현 체크로 연결한다. 새 결과의 문자열만 추가하고 기존 소비자·복원 경로·화면 배선을 그대로 두지 않는다.

**완료 조건:** 기능 비활성, 설치본 불명, 계약 불일치가 신규 검증 PASS로 표시되지 않는다.

RR-T01에는 50–80% 점유 및 최초 제어 주기 기준 1–2초 지연의 중간 구간도 넣어 상태 유지와 3회 연속 복귀 확인을 시험한다. FR-T02와 기존 RR-T04/RV08의 BLOCKED 0건 검증은 FR02에서 정한 dispatch 경계를 사용하며, BLOCKED 이전에 발송한 요청의 완료와 혼합하지 않는다.

각 시험은 기존 관련 fixture에서 한 번에 하나씩 TDD로 진행한다. 정상 경로를 중복 시험 파일로 늘리지 않는다. RV01–RV09·RR-T01–RR-T04·FR-T01–FR-T04의 **17개 추가 시험 명세는 아직 전체 시나리오 미실행**이며, 실패 재현·최소 수정·회귀 검사의 실제 결과와 종료 코드를 각각 남긴다. 아래 단계별 작은 경계 시험을 전체 명세의 통과로 집계하지 않는다. FR-T04는 RR-T04의 구체적인 callback 사례이므로 같은 fixture를 확장하고 중복 성공 실적으로 세지 않는다. 표의 여러 경계 조건도 한꺼번에 구현하지 않고 하나의 실패 행동부터 진행한다.

IC02–IC04는 FR-T02·FR-T04·RR-T04·RV08 내부의 경계 조건이다. 신규 시험 ID나 별도 시험 개수로 늘리지 않는다. 실제 effect 연결처럼 hook mock으로 확인할 수 없는 경계도 해당 기존 시험 명세에 묶어 기록하며, 하나의 결과를 여러 ID의 독립 성공 실적으로 중복 집계하지 않는다.

검사는 실제 writer와 임시 파일을 우선 사용하고, HTTP·시계·쓰기 장애 경계만 제어한다. 시험별로 파일 내용, ID 집합, 결과 집계, 정상 종료 여부를 함께 확인한다.

최종 검사는 저장소에 정의된 다음 절차를 사용한다.

- `npm run health:backend:test`, `npm run health:backend:lint`, `npm run health:backend:typecheck`
- 변경한 현장 검증기의 `pytest` 테스트
- `npm run health:frontend:typecheck`, `npm run health:frontend:lint`, `npm run health:frontend:test`

격리된 테스트 설정을 적용하고 실제 장비 통신은 금지한다. 명령·종료 코드·전체 결과를 보존한다. 기존 실패와 이번 변경으로 생긴 실패를 구분하며, 미해결 핵심 실패가 있으면 완료로 표시하지 않는다.

## 4. ACT — 산출물과 단계별 종료

이 문서가 `docs/01-plan/features/http-persistence-integrity.plan.md`에 저장된 계획 원본이다. 구현 착수 시 이 문서와 기존 사례를 이어서 변경 내역, 테스트 증거와 재개 상태를 기록한다.

- 각 단계 종료 시 변경 범위와 테스트 결과를 정리한다. 새로운 요구가 발견되면 다음 단계 전에 계획을 수정한다.
- CHECK에서는 저장 경로·메타데이터 손상·비밀값 노출·호환성 영향을 함께 검토한다.
