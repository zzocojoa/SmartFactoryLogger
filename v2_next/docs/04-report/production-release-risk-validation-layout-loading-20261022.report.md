# 초기 데이터 로딩 중 화면 배치 이동 재현과 수정

2026-10-22. R2의 VM CLS 초과를 조사하여, 작은 화면에서 데이터 대기 표시가 완성된 카드의
크기를 확보하지 않는 문제를 재현하고 소스를 수정했다. 서버에는 적용하지 않았다.

## 원인과 변경

624×549 화면에서 첫 데이터가 도착하면 공정 KPI 영역이 약140px에서786px로 커지고
아래 SPOT 온도·보조 온도·카메라 영역을 밀어냈다. 원래 `.kpi-card`에는 작은 화면용
min-height760px가 있지만, 로딩 분기는 일반 div만 표시하므로 해당 크기를 확보하지 않았다.
다른 위젯도 초기 일반 div에서 `.card`로 바뀌면서 기존 카드 크기 규칙이 뒤늦게 적용됐다.

초기 재현에서 큰 이동은 자동 스크롤 명령 전에 발생했다. 데이터 응답을800ms 늦춘 별도
대조에서도 스크롤 없이 CLS0.5697을 재현했다. 따라서 자동 스크롤만으로 생긴 현상으로
처리하지 않는다. 단, 원래 VM 실행에는 raw layout-shift sources가 없어 과거7페이지의
각 이동 원인을 직접 확정한 것은 아니다. 이번에는 같은 설치본 화면에서 재현 가능한 원인을 확보했다.

KPI·SPOT 온도·보조 온도·몰드·카메라의 대기 표시에 기존 카드 클래스를 적용하고,
NativeDashboardSurface의 지연 로딩 자리도 카드 크기를 유지하게 했다. 로딩 중 값·상태를
가짜로 표시하지 않고 `Loading...`와 `aria-busy`를 유지한다. 완성된 카드 크기·표시 수치·
수집 주기·백엔드·장비 설정을 변경하지 않았다. 제품 변경은 프런트엔드6파일이다.

## 실제 브라우저 대조

기존240a 설치본에서 추출한 화면51파일을 payload manifest와 해시 대조해 사용했다.
개발 PC의 별도 headless Chromium148.0.7778.96과 loopback 임시 서버에서 실행했다.
실제 제품 backend나 장비·운영 서버에는 접속하지 않았다. 새 임시 브라우저 context를
조건별로 만들고 종료했으며 브라우저와 임시 HTTP 서버도 종료했다.

보존된 health/data/SPOT설정/JPEG 응답을 사용하고 metadata·layout·stats는 명시적인 시험
응답으로 대체했다. 날짜를 최신으로 바꾸지 않았으므로 화면의 STALE 표시를 운영 장애로 해석하지 않는다.
페이지마다5초를 관찰하고 data 응답은800ms 지연했다. headless 실행이므로 작업자 화면 성능
합격 시험이나 기존 VM 전체 비교의 대체 결과가 아니다.

수정 후3조건 모두 기존 목표0.1 이하이며 새 grid 이동 항목0, pageerror0이다.
CLS는 최대 묶음 지표라 모든 개별 이동값을 합산하지 않았다. 별도의 PerformanceObserver로
원시 이동·영향 요소·좌표·스크롤/자동조작 시각을 보존했다. 헤더의 작은 이동은 그대로 관측된다.
요청은 예상된 `/api/layout` 404를 제외하고200이며, 차단된 외부 요청은0이다.
