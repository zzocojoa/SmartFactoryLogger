# AGENTS.md

## Codex App 병렬 운영

Codex app에서 여러 thread/worktree를 사용할 때는
[Codex App 병렬 Thread 운영 규칙](docs/V2/05_운영_배포/codex_app_parallel_thread_operating_rules.md)을
따른다.

기본값:

- Local thread 1개
- Worktree thread 최대 2개
- Subagent는 읽기 작업 전용

공식 문서가 권장 thread 수를 정한 것은 아니다. 이 기준은 SmartFactoryLogger
v2_next의 충돌 방지와 최종 검증 책임을 명확히 하기 위한 내부 운영 규칙이다.

## 서버 검증 경로와 정리

이후 새 서버 검증·배포 준비·백업 도우미는
[서버 검증 경로와 정리 기준](docs/V2/05_운영_배포/server_validation_path_policy.md)을 따른다.
2026-09-20 사용자 지시에 따라 서버·개발 PC 모두 `SFLOps`를 새 작업 경로로 사용하지 않는다.
기본 작업 위치는 실제 사용자 바탕화면의 `SmartFactory` 아래 실행별 새 폴더다.
일반 탐색기에서 접근 가능한지 확인하고, 기준 자료는 묶음에 포함하며 경로는 실행 폴더 기준으로 찾는다.
기존 부모 폴더의 소유권·ACL을 바꾸지 않고, 새 결과 폴더에도 운영 사용자의 읽기 접근을 보장한다.
기존 해시 결합 도우미/증거를 자동 변경·이동하지 않는다. 운영 AppData/설치 폴더는
별도 데이터 이관 없이 이 기준으로 옮기지 않는다. 탐색 결과는 삭제 승인이 아니다.

## 서버 검증 파일 전달 책임

서버 검증이 필요하면 Codex가 개발 PC의 준비뿐 아니라 `Z:\` 전송과
Chrome 원격 데스크톱을 통한 **서버 로컬 최종 폴더 복사까지** 담당한다.
`Z:\`에 올린 것만으로 전달 완료라고 보고하지 않는다. 서버의 실제 절대경로와
파일 존재를 확인한 뒤 실행 방법을 안내한다. 상세 절차와 실행 제한은 위 경로 정책을 따른다.

## 공유 드라이브 폴더 관리

2026-09-20 사용자 지시에 따라 새 전송·회수 폴더는 `Z:\` 루트에 만들지 않는다.
`Z:\SmartFactory\YYYYMMDD\send`(서버 전달), `return`(서버 결과 회수),
`records`(전송·경로 변경 기록) 아래 실행별 폴더로 관리한다.
기존 공유 사본의 위치가 바뀌면 원문·해시 결합 기록은 수정하지 않고 이전/새 경로 대응표를 남긴다.
서버 로컬 실행 폴더와 운영 AppData/설치 경로는 공유 드라이브 정리로 이동하지 않는다.

## 운영본과 롤백 기준의 갱신

2026-10-08 사용자 지시에 따라 특정 commit을 영구 운영 대상으로 고정하지 않는다.
로직 개선 중에는 직전 승인·검증된 운영본을 복귀 기준으로 보존하고, 개선본의 검증과
운영 승격·적용 확인을 마치면 그 버전을 다음 개선 작업의 롤백 기준으로 갱신한다.
현재 기준과 변경 이력은 [운영본·롤백 기준](docs/V2/05_운영_배포/operating_rollback_baseline.md)을 따른다.
운영본·다음 변경의 롤백 기준·이번 교체 전 이전본을 실제 build commit과 installer SHA256으로 구분한다.
과거 묶음의 고정 해시는 당시 바이트의 식별값이며 영구 사용 지시가 아니다. 기존 증거는 재작성하지 않는다.
미서명 내부 운영 승인과 서명·장비 설정 검증·기술 QA 결과를 구분하고, 승인 때문에 미검증을 PASS로 바꾸지 않는다.
기존 승인과 근거가 충분한 동일 설치본에 재승인·재빌드·반복 120분 시험을 자동으로 추가하지 않는다.
새 코드나 설치본에는 변경에 필요한 검증과 해당 승인 범위를 적용한다. 기준 갱신만으로 설치·복구를 자동 실행하지 않는다.
